# IZ4 before migration

`iz4 migrate` converted IZ4 to the Is For format on 2026-09-17. The new
file keeps only what the software is for, who it is for, and the
invariants that must remain true. Everything else it held is kept here
word for word, so nothing was lost. Move each part to wherever it now
belongs - the README, an ADR, tests or issues - or delete what no
longer matters.

## gist

IZ4 answers the question every codebase should answer: what is this
software FOR? IZ is Invariant Zero and iz4 reads 'is for' - an IZ4 file
states what something is supposed to do, in a form humans and machines
can understand and maintain as intent evolves, with Invariant 0 carried
in the name. This project is the open IZ4 file format and the iz4
command-line tool for creating, checking and maintaining IZ4 files
beside source code.

## behaviours

- A project can declare its intent in a root file named IZ4, kept beside its source.
- Additional or standalone intent can be kept in .iz4 documents using the same format.
- Humans can read and edit these files directly in any text editor.
- Software can validate their deterministic structure (iz4 check) and report problems with file and line numbers. check then prints a checklist, one line per fact with a tick for what is true and a cross for what is missing, each cross carrying its remedy: the structure, the Invariant 0 text, invariant numbering and, for a root IZ4, the repository's agent entry points (AGENTS.md always; CLAUDE.md and the skill where the repository shows Claude use) carrying a current managed section. Crosses are file state, not failure: only structural errors set the exit code.
- Entries can be added from the command line while working (iz4 add), without disturbing the rest of the file.
- From any subdirectory, the nearest IZ4 is found by walking upward (iz4 show, check, add, log, diff).
- Git preserves the evolution of intent alongside the implementation (iz4 log, iz4 diff).
- iz4 init drafts the first specification from the codebase's own account of itself (README, changelog, file layout): it hands the scaffold plus that evidence to a configurable agent command and validates the draft before writing it. Without a working agent, init falls back to the plain scaffold, loudly, so it always leaves a file. --/agent skips the agent deliberately. init also sets up agent entry points by default - AGENTS.md always, CLAUDE.md and the skill when the repository shows Claude use - with --/agents to opt out and --agents to force all three; trouble there is a warning, never a failed init, and init never prompts.
- A maintainer can make a IZ4 discoverable by connecting it to the IZ4 register and submitting evidence (iz4 register, iz4 report). Signing up comes first, on the web (iz4.you, email passcode); the CLI guides those steps, stores the connection, and submits evidence itself. A report carries presence, digest, counts and check outcomes - never the text of the IZ4. With --github, iz4 register also sets up GitHub Actions: it writes a workflow that installs iz4 (its runtime cached between runs) and runs iz4 report on every push, so CI evidence carries a real syntax check, and it hands the token to the GitHub CLI on standard input as the repository secret S2R_TOKEN. It never overwrites a different existing workflow without --force, and it leaves committing and pushing to the maintainer. Once connected, iz4 badge prints the public card link and paste-ready Markdown and HTML badge snippets for a README, derived offline from the stored connection; the badge is served live by the register and renders the card's current evidence, so embedding it claims nothing the card cannot back.
- A coding agent can fetch everything it needs to follow a IZ4 in one offline command (iz4 agent): the canonical adherence protocol, the file's byte digest, the inherited Invariant 0, and the specification itself, as delimited text or versioned --json. iz4 agent install writes short managed sections into AGENTS.md (and CLAUDE.md with --claude) and, with --skill, the portable skill - all generated from the one bundled protocol, never copying the project's invariants, preserving surrounding content, idempotent, and refusing malformed markers or symlinks that escape the repository. iz4 agent status reports spec validity, binding resolution and integration state in wording that never claims an agent read anything or that software conforms; --strict turns it into a CI check.
- Every invariant carries a stable, plain monotonic number ('Invariant 3: ...') so humans and agents can refer to it unambiguously: Invariant 0 is the foundation and project invariants start at 1. iz4 add invariant numbers new entries automatically (explicit numbers respected, duplicates refused), iz4 number assigns the next free numbers to any unnumbered invariants in file order without touching existing ones, iz4 show invariant 3 resolves a reference, and iz4 init numbers its agent draft before writing it. iz4 check reports each unnumbered invariant as a warning and a duplicate number as an error.
- The CLI installs with one curl command: the installer fetches the code, fetches the runtime too when it is missing (into the user's home, nothing system-wide), links iz4 onto the PATH and verifies it runs. Nobody needs to know or care what language the tool is written in to install it.
- CI builds iz4 as one standalone file for Linux x86_64, macOS (universal) and Windows x64 with a pinned, checksum-verified Raku++ release, proves each file runs alone, smoke-tests it, runs the full suite against it on Linux and macOS, and keeps the files as build artifacts. Nothing is published by that workflow; distribution is a separate decision.

## constraints

- Implemented in straightforward Raku using core modules only; the only runtime needs are Rakudo and, for log/diff, Git. Agent-assisted init shells out to an external agent command the same way and degrades to the scaffold without one.
- The CLI itself works completely offline: no telemetry, database or cloud requirement, and no account needed for any core command. Exactly two explicit opt-ins may reach the network: the optional agent command behind init, and the register commands (iz4 register, iz4 report) a maintainer invokes deliberately. Every other command never touches the network, and init still works (scaffold) without an agent.
- Plain terminals and SSH: no TUI and no terminal-UI libraries; terse output, no banners.
- Plain-text, line-based format (not JSON, not YAML) so Git diffs stay clean and humans can edit by hand.
- Unknown sections must be preserved and reported as warnings, not errors, so the format can evolve without breaking older files.
- The CLI must work across operating systems and CPU architectures: the tool is pure source, the installer obtains a runtime per platform (prebuilt where one exists, built from source with plain warnings otherwise), and external tools are reached through portable fallbacks (sha256sum, shasum or openssl for digests) - never GNU-only or x86-only assumptions.

## decisions

- 2026-09-17: IZ4 is refocused on enduring invariants (user ruling: help developers discover the few truths worth preserving, never document everything true today). IZ4 means Is For: a file answers what the software is for, who it is for, and what must remain true to keep serving them, with a BECAUSE for each invariant. The canonical format shrinks to four blocks - IS FOR WHAT, IS FOR WHO, INVARIANT n, BECAUSE - and drops gist, behaviours, constraints, decisions, direction and references, whose content belongs in README, ADRs, tests, issues or Git. Invariant 0 is restructured, with every protection kept, into five inherited foundation invariants: 0 humans first, 1 do no harm, 2 human agency, 3 honesty, 4 the foundation holds (which keeps the safe pause and 'no entry may weaken this'). 0-4 are reserved and inherited by every IZ4 without repeating them; project invariants begin at 5. iz4 add and iz4 init coach instead of filling templates: one useful challenge at a time, the golden test (would we regret not telling the people rebuilding it?), a push for a real BECAUSE, and a willingness to say 'this probably is not an invariant' and point elsewhere. Agent drafting moves from init to iz4 suggest, told to make IZ4 small, never complete. Checking keeps verified file facts apart from conformance, which it reports as uncertain. This supersedes the 2026-09-10 rulings that init drafts from the repository by default and never prompts, and it renumbers once: legacy files still parse, and iz4 migrate converts one explicitly, printing the number mapping and keeping every dropped section in a companion file.
- 2026-09-16: The developer's own machine runs the checkout (user ruling: the local version should always be the most up-to-date). The launcher the installer writes runs whatever sits at the installer's checkout path, so on a machine that develops iz4 that path is a symlink to the working tree, and the installer treats a symlink there as a developer's checkout: it says so and never pulls over it. Nobody else's install changes; a clone there is still updated by re-running the installer.
- 2026-09-16: iz4 check reports whether the agent entry points are set up, as a checklist (user ruling: ticks against what is true, a cross where something is missing, and how to remedy it). Until now only iz4 agent status looked at AGENTS.md, CLAUDE.md and the skill, and only one repository in this estate had them installed, so the file everyone runs on every IZ4 now shows them too, reusing the same file-state checks and the same claim-nothing wording. A cross never changes the exit code: Invariant 5 keeps check structural and the 321 deploy gate keys off that code, so a repository without AGENTS.md is told how to fix it, not blocked. The glyphs are one character per line, coloured only on a terminal (never under NO_COLOR or a pipe), which stays inside the plain-terminal constraint.
- 2026-09-16: Every invariant is numbered, starting at Invariant 0 (user ruling: so each can be referred to unambiguously elsewhere), recorded as Invariant 9. Until now numbering was optional and only iz4 add applied it, which left 23 of the 24 IZ4 files in this estate with numbered additions sitting after unnumbered originals - exactly the ambiguity the numbers exist to remove. Numbering is now the rule: check warns for each unnumbered invariant (a warning, not an error, so existing files stay green and deploys are not blocked while the estate catches up); the new iz4 number command assigns the next free numbers in file order and never renumbers an existing entry, because numbers are references and Invariant 7 forbids silent rewrites - it is an explicit command that changes only the first line of each entry it numbers; add points out unnumbered neighbours after adding; and init numbers an agent draft before writing it, since a fresh draft is not yet anyone's file.
- 2026-09-15: SPOZ2 is renamed IZ4 (user ruling, explicitly authorising the rewrite of Invariant 8). The name answers the file's question - what is this software FOR - and carries the foundation in it: IZ is Invariant Zero, iz4 reads 'is for', and iz4.you is Invariant 0's promise. The root intent file is IZ4, further documents use .iz4, the command is iz4 (spoz2 kept as an alias), the brand domain is iz4.you and spoz2.do will redirect permanently. Legacy keeps working, read silently: SPOZ2 root files and headers, .spoz2 documents, .spoz2-register connections, the old token store, SPOZ2_* environment variables and SPOZ2-AGENT markers. Invariant 0's text and digest are unchanged. The GitHub repository becomes cli.iz4.you (old URLs redirect); the local checkout path move is deferred so running sessions are not cut off; and iz4.you's DNS is not yet on the live box, so printed iz4.you links go live when the user moves the records.
- 2026-09-13: Invariant 0 strengthened (explicitly authorised by the user). Objectives cannot override the human protections: when an objective conflicts with them, the protections are preserved, the conflict is reported, and the affected action pauses safely - and honesty now extends to what remains uncertain or blocked. New canonical sha256 1af8b123edd8...; earlier texts and digests stay in this history unchanged. Protocol rule 5 gains the same pause-and-report behaviour: continue safe work within existing authority, resume only via a compliant approach or the deliberate intent-change process, and Invariant 0 cannot be waived by a project-level approval. Pausing follows the system's own responsibilities and safe procedures; a reported block does not establish that an invariant passed, and none of this claims runtime enforcement.
- 2026-09-13: spoz2 badge closes the loop from repository to card (user ruling: the CLI should point at the badge and card). It derives the card and badge URLs and the Markdown/HTML snippets offline from the reports URL already stored in .spoz2-register - no new network path, no account lookup - and its output states that the badge only renders what the card's evidence backs.
- 2026-09-13: There is no 'SPOZ2 0.0' (user ruling: just call it Invariant 0, everywhere). The header is the bare word SPOZ2; the format carries no version number, and the canonical Invariant 0 is one current text identified by its digest, evolving in Git like everything else. The tool reads legacy 'SPOZ2 <n>' headers silently and writes the bare header; every message, document and page says 'Invariant 0', never 'invariant zero' or a format version. If release versioning is ever needed, that is a fresh decision - today it was complexity nobody used.
- 2026-09-12: Invariant numbers are plain monotonic integers (user ruling: the dotted 0.0 just adds complexity). The foundation invariant is 'Invariant 0'; there is no dotted numbering and no reserved 0.x space, and project invariants start at 1. Format 0.0 is still in development, so the canonical text and digest changed in place (sha256 df43776d2c4d...); the tool still recognises the older 'Invariant 0.0:' and frozen 'Invariant zero:' leads in existing files, which check flags as drift that binds regardless.
- 2026-09-12: Invariants are numbered so they can be referred to explicitly (user ruling). The number lives in the entry text - 'Invariant 3: ...' - following the Invariant 0.0 convention, so the grammar is unchanged and unnumbered files stay valid: check never nags them, and numbers appear as entries are added. add assigns the next free integer automatically, show invariant N resolves a reference, duplicate numbers are check errors because they defeat the reference, the agent-drafting prompt asks for numbered invariants, and the 0.x space stays reserved for the format's foundation. This file's own invariants are now numbered 1 to 8.
- 2026-09-11: The CLI works across architectures (user ruling). The code needed nothing - Raku is architecture-independent - so the work is at the edges: the installer falls back from a prebuilt runtime download to 'rakubrew build' with honest compiler-and-make prerequisites and a named platform, and file digests fall back sha256sum -> shasum -> openssl so macOS and the BSDs work without GNU coreutils. Linux and macOS are covered by the installer on any architecture rakubrew can download or build for; Windows is documented as manual (rakudo.org plus the clone-and-symlink steps). Verified on this x86-64 Linux box only; other platforms are covered by design and the known-digest test, not yet by execution.
- 2026-09-10: init does a lot automatically by default (user ruling: don't make me think - no command-line options to look up). One command drafts the spec and installs the agent entry points it detects, safe because managed sections preserve surrounding content and are idempotent; --/agents opts out, --agents forces everything, and nothing ever prompts. This supersedes the same-day choice to prompt interactively and require an explicit flag in scripts.
- 2026-09-10: Practical agent adherence lives in the CLI and stays harness-agnostic (agent-adherence brief, plus the user's ruling to ship an official portable skill). One canonical protocol is bundled in the tool; spoz2 agent prints it in a self-contained packet, and every integration is generated from it: thin managed sections that point at the command, and the skill, which embeds the protocol so the core workflow works by reading the file directly - while stating that CLI validation and inherited-binding resolution were skipped. Wording is kept honest everywhere: a packet proves nothing was read, installed integrations are statements about files, spoz2 check stays structural, and evidence of conformance remains the agent's reported checks, not a tool claim. Additive only; no invariant weakened, and no dependency on any particular harness, model, editor or registry.
- 2026-09-10: Installation is one curl command (user ruling: much easier, and people may not even need to know it uses Raku). The repo ships a POSIX-sh installer served raw from GitHub; when no runtime is present it fetches Rakudo via rakubrew into the user's home instead of asking them to care, writes a launcher into ~/.local/bin, and every failure path ends with plain instructions. A branded install URL on a spoz2.do domain is a later DNS decision.
- 2026-09-10: The user ruled the CLI should let a maintainer register a SPOZ2 so it is discoverable, signing up first. Sign-up stays on the web (register.spoz2.do, email passcode - a CLI cannot read your email); spoz2 register guides onboarding and stores the connection: the reports URL in .spoz2-register beside the file, the token under ~/.config/spoz2 and never in the repository. spoz2 report submits the register's s2r-report evidence (presence, digest, counts, check outcome) via curl, shelled out to like Git. Register errors are advisory - exit 0 unless --strict - matching the register's checks-never-block invariant. The core stays offline and the open format carries no registry fields.
- 2026-09-10: The numbering is retro-fitted to start from 0.0 (user ruling: version 0.0 is what is being developed, and there are no other users yet, so the renumber is safe).  The 0.1 to 0.4 ladder of the past two days collapses into the single in-development SPOZ2 0.0, whose canonical invariant zero is the HUMANS FIRST text; the ladder's history stays in git.  Version immutability discipline (frozen text and digest per version, changes only via a new version with a public change record) begins with the first release.
- 2026-09-10: Format 0.4, ruled by the user: the headline tightens to 'humans first'.  0.3 (published minutes earlier, adopted by no file) is superseded, not rewritten: its text and digest stay in the record, which is the version rule surviving its first temptation.
- 2026-09-10: Format 0.3, ruled by the user: the designation becomes 'Invariant 0.0' (retro-fitting the name; the clauses are unchanged from 0.2), reserving the 0.x space for the foundation.  The 0.2 text and digest stay frozen; the tool reads 0.1, 0.2 and 0.3 and recognises both leads.
- 2026-09-10: Format 0.2, ruled by the user: invariant zero gains its full canonical wording (purpose, dignity, agency, honesty, precedence), published with a digest per version. 0.1 keeps its original text and digest; this file moved to 0.2 explicitly. The tool now reads both versions, seeds the 0.2 text, verifies the binding per declared version, and reports exactly what a check verified. Deliberately no inaction clause: invariant zero governs what software does, not everything it fails to prevent.
- 2026-08-23: This project is Customer Zero. SPOZ2's own SPOZ2 is the first real use, and the format changes only from what that use teaches.
- 2026-08-23: Raku, so the author can read and change the tool quickly; startup time and portability matter more than cleverness.
- 2026-08-23: The format is a tiny line-based grammar (header, 'name:' sections, indented '- ' entries) rather than JSON/YAML or a DSL; continuation lines join with a space, so entries can be wrapped.
- 2026-08-23: History and diffs come from Git. spoz2 log/diff are thin wrappers; there is no internal version control.
- 2026-08-23: 'decisions' and 'direction' became known sections during dogfooding, because there was nowhere to record why choices were made or where intent is heading without presenting it as implemented behaviour.
- 2026-09-06: The user ruled this dialect (SPOZ2 0.1 header, gist/sections, git-kept history) is THE SPOZ2 format, superseding the version-bound since/until dialect. This tool is now the public reference implementation at github.com/nige123/cli.spoz2.do; the earlier dialect's repo was removed on 2026-09-07 and survives only as a local git bundle (~/archive/app.spoz2.do-prototype.bundle).
- 2026-09-07: init is agent-assisted by default (ported from the versioned prototype) because a scaffold-only init kept surprising the maintainer - the point of init is extracting what the project is supposed to do. The agent is an external command (SPOZ2_AGENT_CMD, default 'claude -p') shelled out to like Git: the CLI itself makes no network calls and still works without it.
- 2026-09-09: The user ruled that every SPOZ2 leads its invariants with invariant zero - humans come first - stated positively (help humans thrive; never harm one, never help anyone harm one; it wins any conflict). init seeds it first in both the scaffold and agent-drafted paths; check warns, never errors, when it is missing or not first, so existing files stay green while adoption catches up.
- 2026-09-10: spoz2 register --github (user ruling, alongside the one-paste Connect CI on the register): it writes a GitHub Actions workflow that installs spoz2 with its runtime cached and runs spoz2 report, which fixes the gap where CI reports from the plain reporter carried checks.syntax not_run and could never qualify a project for its SPOZ2 badge. The token reaches the GitHub CLI on standard input, never argv; committing and pushing stay with the maintainer. The sign-up address moved to spoz2.do with the register's domain.
- 2026-09-11: The CLI stays within what both Rakudo and Raku++ run, so it can ship as a standalone binary built by Raku++ (user direction: binaries for Linux, macOS and Windows). Two Raku++ 3.26 differences were met: (@a, @b) := binding flattens both lists into the first array, so marker lines unpack into scalars; and a <{...}> regex interpolation in one test became starts-with. SPOZ2_TEST_BIN points the suite at a compiled binary, so CI tests the executable it ships.
- 2026-09-11: CI compiles spoz2 with Raku++ --aot, not --bundle. Raku++ 3.26's bundle stub declares the module length as unsigned long, which is 32-bit on Windows, so MSVC cannot link it and a MinGW build carries no modules. --aot parses at build time, avoids the stub, and passes the whole suite on Linux.
- 2026-09-11: How each binary links. Linux links libstdc++ statically, so glibc is its only dependency; its floor is glibc 2.38 (Ubuntu 24.04, Debian 13, Fedora 39 or newer), set by the Raku++ 3.26 Linux runtime itself, so building on an older system cannot lower it. macOS is one file holding arm64 and x86_64. Windows uses the MSVC build, which needs only system DLLs; a MinGW build is linked fully static or it needs MinGW DLLs beside it.
- 2026-09-11: Windows binaries come from the Raku++ MSVC archive only; its file needs only system DLLs. A MinGW file needs MinGW DLLs beside it, and linked with -static it crashes at start (Raku++ 3.26). macOS files declare macOS 11 as their minimum, matching the Raku++ runtime; left to the default they would require the runner's own macOS.
- 2026-09-12: Invariant 0 rewritten short and scannable while format 0.0 is in development: 62 words in five plain sentences, sha256 b0c2482d4298, replacing the 118-word original (sha256 df43776d2c4d). The meaning is unchanged: thrive and dignity, no harm, humans in charge, honesty, and nothing may weaken it. Files carrying the old wording still bind, and check reports the difference.

## direction

- Make a IZ4 directly useful to AI coding tools that simply read it; later, possibly a command that prints a compact context block for them.
- The wider iz4.com/iz4.you vision (certification, commitments, standards intelligence) is out of scope for this CLI and must not leak into the open format. The register client commands are the one deliberate bridge; the format itself stays registry-free.
